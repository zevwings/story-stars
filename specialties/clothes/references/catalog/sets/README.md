# 成套装束（Sets）

本目录只收 `record_kind: set` 的稳定多件套。返回 [套组索引](_index.md) 或 [Catalog 说明](../README.md)。分类权威见 [衣装结构与穿着层级](../../components/衣装结构与穿着层级.md)，内容与证据要求见 [衣装档案写作规范](../../components/衣装档案写作规范.md)。

## 套组准入

Set 至少包含两个核心基础衣装单元，并具有不依赖临时搭配的稳定整体身份。配套剪裁、连接关系、纹样或主题识别应说明：替换核心单元后，为什么该整体身份不再成立。

原生内衣、原生比基尼各自是一个 Piece，不因内部有两个部件就成为 Set。它们与专属外衣、鞋履或配饰共同形成更高层稳定装束时，才判断新的 Set；不为同一内衣或泳装另建用途不同的重复档案。

单件婚纱、连衣裙、连体裤仍是 Piece。普通衬衫＋半裙、泳衣临时搭罩衫和草帽不自动成为 Set；同时出现的多人造型也不自动具有一个整体身份。Set 不要求配齐全部穿着层。

## 按主要用途进入目录

| 目录 | 稳定套组的典型范围 |
| --- | --- |
| [daily](daily/_index.md) | 原生通勤西装、由多个基础单元构成的日常稳定装束 |
| [intimate](intimate/_index.md) | 内衣单元与专属外衣等共同形成的稳定私密主题装束 |
| [swimwear](swimwear/_index.md) | 泳装单元与专属罩裙等构成的稳定整体装束；比基尼本身归 Piece |
| [sport](sport/_index.md) | 原生运动上衣＋运动裤等运动套组 |
| [cos](cos/_index.md) | 由多个核心部件共同形成角色识别的主题套组 |
| [stage](stage/_index.md) | 原生舞台演出套组 |
| [ceremonial](ceremonial/_index.md) | 礼服主体与专属披肩、外裙等共同形成稳定身份的礼仪套组 |
| [action](action/_index.md) | 具有稳定结构与用途的行动、战术套组 |

主要用途只能选一个，其他合理用途写兼容用途，不为同一实体建立多个目录副本。内衣不自动等于私密用途；普通沙滩外搭也不能使一件泳衣自动升级为套组。

## 相邻用途的划分

先判断稳定套组身份，再根据来源证据和主要设计目的选择用途；不能仅凭拍摄地点、露肤程度或装饰多少分类。

- `daily` 与 `intimate`：按整体装束的主要穿用目的区分；其中包含内衣不自动使整体成为 `intimate`。原生内衣单元自身仍归 Piece。
- `swimwear` 与 `daily`：泳装套组以游泳或水域穿用为主要目的；普通夏日两件套不因在沙滩拍摄就归泳装。
- `sport` 与 `daily`：结合运动设计与穿用条件判断；运动风外观不自动证明专业运动用途。
- `cos` 与 `stage`：角色或主题识别是主要身份时归 `cos`；以演出设计为主时归 `stage`，合理的次要用途写兼容用途。
- `ceremonial` 与 `stage`：礼仪活动与舞台演出分别判断；华丽程度不能替代主要用途。
- `action` 与 `cos`：结合实际行动用途与结构证据判断；战术外观或制服扮演不自动成为行动装备。

## 与基础单元的关系

- 原生套组可以直接建立，不要求先拆出全部 `piece`。
- 套组必须自足描述核心组成；某个部件没有独立 CLO，不影响在“包含单件”中完整记录。
- 确实需要独立维护和跨造型复用的基础单元，才另建不同 ID 的 `piece`。原生内衣和泳装单元的内部部件不自动拆档。
- 已有单件可作为组成导航，但链接不能代替套组对本次核心部件的必要描述。
- 人物采用套组后仍需补齐实际穿用条件，并在人物衣装或 Construction 中自足保存采用规格；Catalog 不代替正式 owner。

## 组成语义

- `### 包含单件`：至少两个构成整体身份的核心基础单元；一个原生内衣或泳装内部的上下装只算一个单元。
- `### 必需层`：穿用不可缺少、但不属于套组固有身份的层次，有实际内容时添加。不可为满足完整感虚构不可见内层。
- `### 可选单件`：移除后不破坏套组身份的扩展，有实际内容时添加。

每个小节只使用一个非空列表。未另建档的基础单元可以直接描述；字段名“包含单件”“可选单件”沿用公共结构，在本项目按基础单元解释。

## 档案结构速查

文件名、frontmatter 与 H1 使用同一实际 ID；frontmatter 仅包含 `schema: clothes.catalog@3`、`id`、`record_kind: set`。实际生成与校验以锁定公共协议为准。

正文按以下顺序组织：

1. `## 分类`：一张两列表，必填 `主要用途`，存在兼容用途时才增加该行；不使用“组合形式”字段。
2. `## 组成`：必含 `### 包含单件`，按实际内容增加 `### 必需层`、`### 可选单件`。
3. `## 来源与边界`：区分直接观察、文档明示、不确定观察与项目设计。
4. `## 结构与使用`：说明套组自身的结构、色材、跨部件关系、固定、穿脱与活动条件。
5. `## 使用条件与叙事作用`：说明季节、环境、功能和适用边界。
6. 主用途或兼容用途包含 `intimate` 时，追加 `## 张力与互动语法`；其他套组不无条件添加。
7. 实际采用内容已自足写入正式 owner 并完成校验后，末尾追加 `## 正式去向`，只保留一个非空、不重复的项目相对路径列表。

不添加公共协议未定义的 frontmatter 字段或 H2/H3，不保留空标题和占位内容。
