# Story Stars 衣装结构与穿着层级

本文件定义项目怎样区分成套装束、可复用单件和不落盘的临时搭配，并规定正文中的结构组成、单件类型和穿着层级。它不保存实际衣物，不分配 `CLO-*`。

## 一、五条独立判断轴

每份衣装档案分别判断以下各轴，不能用一个词替代其它轴。

### 1. 档案粒度

- `look`：具有固有完整身份的成套装束。
- `piece`：具有独立复用价值、但仍需搭配或单独维护的实际衣物／穿戴配饰。
- 临时搭配候选：若干 `piece` 为人物或场景临时组成的方案，不是第三种 `record_kind`，不进入 catalog。

### 2. 结构组成

只用于 `look`：

- `single-piece`：一个结构自足的主体本身就是完整装束，例如连衣裙、旗袍或连体衣；基础内层、鞋履和轻配饰不改变这一判断。
- `multi-piece`：多个部件因固有设计、结构语言、纹样、标识或角色／作品识别共同形成不可随意替换的装束身份。

### 3. 单件类型

只用于 `piece`：

- `top`：上身主体、外搭或覆盖层，包括衬衫、胸衣式上装、背心、外套和罩衫。
- `bottom`：裙、裤、裙裤、围裹式下装。
- `one-piece`：实际单件的一件式衣物，例如连衣裙、连体衣、旗袍式主体或整体泳装；它仍可能因档案目的不同被管理为 `look + single-piece`。
- `hosiery`：丝袜、连裤袜、长袜、短袜和腿套。
- `footwear`：鞋、靴、凉鞋和拖鞋。
- `accessory`：首饰、腰带、手套、帽、发饰、包、披肩及其它穿戴配件。

不新增 `other`、`outerwear`、`underwear` 等 frontmatter 枚举。更细类别写在正文“具体类型”和“穿着层级”中。

### 4. 用途

`primary_use` 只能有一个：

- `daily`
- `stage`
- `ceremonial`
- `intimate`
- `sport`
- `swimwear`
- `action`
- `cos`

其它合理用途进入 `compatible_uses`。同一实体不得因用途不同复制到多个目录。

### 5. 穿着层级

穿着层级只写正文，不新增 schema：

- 贴身基础层；
- 主体层；
- 覆盖／外搭层；
- 腿部层；
- 足部层；
- 点睛／功能配饰层。

同一件衣物在不同场景可能承担不同层级，但其实际结构身份不因此改变。

## 二、`look` 的严格准入

### 可以作为 `look`

- 连衣裙、旗袍、连体衣等结构自足的一件式装束；
- 完整 COS、制服、礼服套装、舞台套装或成套私密装束，部件共享不可随意替换的设计系统；
- 多个部件共享稳定纹样、配色、边缘、五金、标识或角色识别；
- 拆开或替换关键部件后，原装束身份消失，而不只是风格略有变化；
- 档案能够自足说明其固有组成，不需要设计者临时补完关键部件。

### 不得作为 `look`

- 吊带上衣＋牛仔短裤；
- 衬衫＋半裙；
- 针织衫＋长裤；
- 普通泳衣临时搭罩衫、拖鞋和草帽；
- 任何只因比例、配色、场合或模特表现得好看而成立的普通单品组合。

“图片里东西很多”“搭好后能直接出门”“上下装在这张图中缺一不可”都不是 `multi-piece look` 的充分条件。

### 判定问题

依次回答：

1. 这本身是什么成套装束？
2. 是否具有不依赖当前模特和场景的稳定身份？
3. 多个部件是否共享不可随意替换的设计系统？
4. 替换关键部件后，是身份消失，还是只变成另一套普通搭配？
5. 是否还需要补一个关键服装决定才能使用？

如果答案只是“这些单件这一次怎样搭”，就不是 `look`。

## 三、`piece` 的建立门槛

只有同时具有实际对象和独立复用价值的单件才建立 `piece`：

- 有明确、可复述的结构身份；
- 能跨多个造型复用；
- 对比例、风格、张力或动作有独立贡献；
- 有稳定的搭配要求或禁忌；
- 能在不依赖原图的情况下自足描述；
- 未来 `$clothes-designer` 可以直接检索并使用。

不要因为图片里“看得到”就机械拆件。斜襟、吊带、鱼骨、花边、拉链等是结构或术语，不是天然独立的 `piece`。

## 四、来源材料与项目实体不是一一对应

一份来源材料允许形成：

- **零个实体**：没有足够证据，或没有任何值得独立维护的对象；
- **一个实体**：明确管理一个完整装束或一个主体单件；
- **多个实体**：普通组合中有多个真正可复用的单件；
- **合并候选**：多份来源材料可能描述同一实体，但必须先核验证据和 ID。

一个源 ID 不得复制给拆出的多个实体。ID 分配、冲突和状态服从 package 协议；无法判断时停止该条，不猜测。

## 五、`look` 的组成语义

### `included_pieces`

记录构成该装束身份的实际部件。某个部件不必另有独立 `CLO-*` 才能在此出现。

### `required_layers`

记录使用该装束时不可缺少但未必承担外观识别的穿着层，例如必要内层、安全层或结构支撑层。不得为满足完整感虚构看不见的内层。

### `optional_pieces`

记录不改变装束身份、但可随场景加入或移除的鞋履、外搭和配饰。

### 部件联动

每个 `multi-piece look` 还要说明：

- 哪些颜色、纹样、边缘、系带或五金跨部件重复；
- 哪个部件承担主体焦点，哪些负责承接；
- 材质关系是统一、递进还是对比；
- 替换哪些部件会使其退化为普通搭配。

## 六、单件的搭配语义

### `pairing: standalone`

单件可作为主要可见主体独立成立，但仍可能需要基础内层或常规鞋履。

### `pairing: required`

缺少特定角色就无法形成可穿用或符合用途的方案。正文必须明确 `required_roles` 和约束。

### `pairing: optional`

单件可使用，但搭配特定部件会改变完整度、比例、风格或环境适配。

`pairing` 描述单件的搭配需要，不表示多个单件已经构成新的 `look`。

## 七、穿着层与组成检查

对每个实体按实际相关性检查：

| 层级 | 观察内容 |
|---|---|
| 贴身基础层 | 贴肤、承托、安全、透痕、肩带或闭合件外露 |
| 主体层 | 主要轮廓、比例、颜色、图案和身份识别 |
| 覆盖／外搭层 | 开合、体积、保暖、防护和动作限制 |
| 腿部层 | 覆盖终点、透明度、压缩、下滑、卷边和勾丝 |
| 足部层 | 重心、步态、抓地、稳定、路面和长时穿着 |
| 配饰层 | 焦点、身份、功能、重量、摆动、声音和勾挂风险 |

需要区分：

- **可见部件**：当前画面或档案确定存在；
- **必要内层**：穿用或结构必需，但不一定可见；
- **可选配件**：移除后不破坏核心身份；
- **设计建议**：项目为了角色或场景新增，不得混入来源事实。

## 八、结构描述最低维度

每个实体按实际对象说明：

- 具体款式；
- 廓形；
- 合体度、松量、支撑、压缩和塑形；
- 腰线、长度和身体锚点；
- 领口、肩背、袖型、腰胯、裤裙线或鞋面结构；
- 省道、分割线、拼片、褶裥、抽褶、斜裁、开衩等关键结构；
- 覆盖与露肤边界；
- 固定、闭合、调节、承重和系带；
- 穿脱顺序；
- 坐、立、行走、抬臂、弯腰、奔跑、涉水等相关动作；
- 上窜、下滑、卷边、走位、扭转、堆积、张口、勒痕等失效风险。

具体术语按 [服装术语与观察词典](服装术语与观察词典.md) 使用；看不清时写可证实的通俗描述。

## 九、季节与环境

- 季节只用春、夏、秋、冬的一个或多个明确值；
- 四季适用时写“春、夏、秋、冬”，不用“全年”；
- 室内恒温、空调环境、过渡季、雨季、海边、舞台强光等写在环境补充；
- 季节判断必须结合覆盖、厚薄、透气、保暖、内层和活动强度；
- 证据不足时写“未判定”及原因，不根据颜色或用途硬猜季节。

## 十、分类流程

```text
确认实际对象
  → 判断是否具有固有完整装束身份
    → 是：look
      → 判断 single-piece / multi-piece
    → 否：逐件判断独立复用价值
      → 成立：piece
      → 不成立：不建档
  → 判断主用途与兼容用途
  → 判断单件类型或 look 的实际部件角色
  → 记录穿着层级、季节和结构
  → 普通组合只保留为临时搭配方向
```

最终检查：档案粒度、结构组成、用途、单件类型和穿着层级必须分别成立。
