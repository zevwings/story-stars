# Story Stars 衣装结构与穿着层级

本文件是 Story Stars 项目唯一的衣装分类解释权，基于 Clothes Specialty 当前协议的项目分类覆盖机制，定义成套装束、可复用基础衣装单元和不落盘临时搭配的边界，并规定正文中的结构组成、单件类型和穿着层级。它不保存实际衣物，不分配 `CLO-*`。

## 一、四条独立判断轴

每份衣装档案分别判断以下各轴，不能用一个词替代其它轴。

### 1. 档案粒度

- `set`：至少两个基础衣装单元共同形成、具有固有完整身份的整体装束。基础单元不必各自拥有独立 CLO 档案。
- `piece`：可独立维护和复用的基础衣装单元，通常是一件衣物或穿戴配饰；原生配套内衣、泳装允许以多个物理部件共同组成一个单元。一件式衣物仍是 `piece`。
- 临时搭配候选：若干 `piece` 为人物或场景临时组成的方案，不是第三种 `record_kind`，不进入 catalog。

本项目通过公共协议的项目分类覆盖明确上述边界：物理部件数量不直接决定档案粒度。内衣、泳装的原生配套关系须有来源或经确认设计依据，不能只凭同色、同图或一次穿着认定。其它普通上装＋下装组合不得借此合写为 `piece`。

机器字段 `record_kind: piece`、分类表字段 `单件类型` 和九种类型值继续沿用；“单件类型”在本项目表示基础单元品类。该覆盖不新增 frontmatter、用途枚举或正文标题。

### 2. 基础单元类型（字段：单件类型）

只用于 `piece`：

- `top`：上身主体、外搭或覆盖层，包括衬衫、胸衣式外穿上装、背心、外套和罩衫；内衣和泳装分别归 `bodysuit`、`swimsuit`。
- `bottom`：裙、裤、裙裤、围裹式下装；内裤与泳裤分别归 `bodysuit`、`swimsuit`。
- `dress`：没有分离裤腿结构、以裙摆为主体的一件式衣物，包括连衣裙、旗袍、单件礼服和睡裙。
- `jumpsuit`：上下身连续且具有两条分离裤腿结构的一件式衣物，包括连体裤、连身工装和 romper。
- `bodysuit`：内衣与贴体连体衣基础单元，包括独立文胸、内裤、塑身衣、连体内衣和原生配套上下内衣；也保留无独立裙摆或分离长裤腿的时装 body、体操服、单件 COS 连体主体的结构归口。后者不因此被判定为内衣或私密用途。
- `swimsuit`：泳装基础单元，包括连体泳衣、独立泳装上衣、泳裤和原生配套比基尼；普通围裹裙、罩衫不因用于海边就归入本类。
- `hosiery`：丝袜、连裤袜、长袜、短袜和腿套。
- `footwear`：鞋、靴、凉鞋和拖鞋。
- `accessory`：首饰、腰带、手套、帽、发饰、包、披肩及其它穿戴配件。

不新增 `one-piece`、`other`、`outerwear`、`underwear`、`suit` 等分类表枚举。更细类别写在正文描述中。

### 3. 用途

“主要用途”只能有一个：

- `daily`
- `stage`
- `ceremonial`
- `intimate`
- `sport`
- `swimwear`
- `action`
- `cos`

其它合理用途进入“兼容用途”。同一实体不得因用途不同复制到多个目录。

用途不能替代结构分类，也不新增 `tags` 或复合枚举。典型交叉判例如下：

| 实际对象 | `record_kind` | 结构字段 | 用途字段 | catalog 目录 |
|---|---|---|---|---|
| 一个物理独立的情趣短裙／半裙 | `piece` | `单件类型=bottom` | `主要用途=intimate` | `catalog/pieces/bottom/` |
| 一件式情趣连衣裙／睡裙 | `piece` | `单件类型=dress` | `主要用途=intimate` | `catalog/pieces/dress/` |
| 原生固定的情趣上衣＋短裙套组 | `set` | — | `主要用途=intimate` | `catalog/sets/intimate/` |
| 本质为日常裙装，只能兼用于私密场景 | `piece` | 按实际结构选择 `bottom` 或 `dress` | `主要用途=daily`，“兼容用途”包含 `intimate` | 对应“单件类型”目录 |

短、透、露肤多或带蕾丝不自动等于 `intimate`；以设计的主要穿用目的和档案证据判断。`piece` 按基础单元的品类和结构进入九种类型目录，只有符合多件套准入的装束才按用途进入 `catalog/sets/`。

### 4. 穿着层级

穿着层级只写正文，不新增 schema：

- 贴身基础层；
- 主体层；
- 覆盖／外搭层；
- 腿部层；
- 足部层；
- 点睛／功能配饰层。

同一件衣物在不同场景可能承担不同层级，但其实际结构身份不因此改变。

## 二、`set` 的严格准入

### 可以作为 `set`

- 完整 COS、制服、西装套装、礼服套装、舞台套装、成套私密装束或泳装主题整体装束，并且至少有两个核心基础衣装单元；
- 多个部件共享稳定纹样、配色、边缘、五金、标识或角色识别；
- 拆开或替换关键部件后，原装束身份消失，而不只是风格略有变化；
- 档案能够自足说明套组自身的固有核心分件；人物真实穿用所需的内搭、外搭、鞋履或其它必需层可以由 `clothes-designer` 补齐。

### 不得作为 `set`

- 原生配套文胸＋内裤、原生比基尼上下装：分别作为一个 `bodysuit`／`swimsuit` 基础单元维护，不再建立相同内容的 `set`；

- 连衣裙、旗袍、单件礼服、睡裙、连体裤、连体紧身衣、一件式泳装或物理上不可拆分的单件 COS 主体；
- 吊带上衣＋牛仔短裤；
- 衬衫＋半裙；
- 针织衫＋长裤；
- 普通泳衣临时搭罩衫、拖鞋和草帽；
- 任何只因比例、配色、场合或模特表现得好看而成立的普通单品组合。

“图片里东西很多”“搭好后能直接出门”“上下装在这张图中缺一不可”都不是 `set` 的充分条件。

### 原生套装与分件

- 来源本身是稳定整体装束时，先排除内衣、泳装基础单元，再判断 `set`；不要求先把全部组成拆成独立档案。
- 整体装束中只有确实需要独立维护的基础单元才另建 `piece`；未独立建档的单元仍可完整写在“包含单件”。内衣、泳装单元的文胸、内裤等内部部件直接在“结构与使用”中描述，不为偶尔单独穿用自动拆出 CLO。
- 同一来源既形成 `set` 又形成若干 `piece` 时，各实体必须拥有不同的 `CLO-*`，并明确它们的从属与复用关系。
- 原生内衣、泳装按完整单元只维护一个 CLO，不同时建立“上装、下装、套组”三份重复档案；来源仅有独立衣物时可以单独建档，不虚构配套件。其它普通多件组合不得仅为减少文件合写为 `piece`。已有重叠记录需先核对来源、身份和全部引用，再另行处理，不自动合并或删除。

### 常见边界

- 西装外套、马甲属于 `top`，西裤或西装裙属于 `bottom`；具有固定面料、剪裁和成套身份的两件套／三件套可另建 `set`，但不新增 `suit` 类型或目录。
- 单件晚礼服、婚纱或宫廷长裙属于 `piece + dress`；只有礼服主体与斗篷、披肩、胸衣、外裙等至少两个基础单元共同形成稳定身份时，才是 `set`。
- 连体泳衣和原生比基尼都属于 `piece + swimsuit`。泳装单元与专属外搭等形成稳定更高层身份时才考虑 `set`；临时加入普通罩衫、拖鞋、草帽不构成 `set`。
- 独立泳装上衣、泳裤归 `swimsuit`；独立文胸、内裤归 `bodysuit`。已作为完整原生单元维护的上下装，在同一档案中描述分件，不再为同一对象补建 `sets/daily`、`sets/intimate` 或 `sets/swimwear`。

### 判定问题

依次回答：

1. 对象是否已构成一个基础衣装单元（含原生内衣、泳装）？若是，按 `piece` 判断；否则确认至少有两个核心基础单元。
2. 这本身是什么成套装束？
3. 是否具有不依赖当前模特和场景的稳定身份？
4. 多个部件是否共享不可随意替换的设计系统？
5. 替换关键部件后，是身份消失，还是只变成另一套普通搭配？
6. 缺少的是套组自身的核心分件，还是人物真实穿用时的必需层？前者说明 `set` 身份未闭合，后者留给 `clothes-designer`。

如果答案只是“这些单件这一次怎样搭”，就不是 `set`。

## 三、`piece` 的建立门槛

只有同时具有实际对象和独立复用价值的基础衣装单元才建立 `piece`：

- 有明确、可复述的结构身份；
- 能跨多个造型复用；
- 对比例、风格、张力或动作有独立贡献；
- 有稳定的搭配要求或禁忌；
- 能在不依赖原图的情况下自足描述；
- 未来 `$clothes-designer` 可以直接检索并使用。

不要因为图片里“看得到”就机械拆件。斜襟、吊带、鱼骨、花边、拉链等是结构或术语，不是天然独立的 `piece`。

## 四、来源材料与项目实体不是一一对应

一份来源材料允许形成：

- **零个实体**：没有足够证据，或没有任何值得独立维护的对象；
- **一个实体**：明确管理一个完整装束或一个主体单件；
- **多个实体**：普通组合中有多个真正可复用的单件；
- **合并候选**：多份来源材料可能描述同一实体，但必须先核验证据和 ID。

一个源 ID 不得复制给拆出的多个实体。ID 分配、冲突和状态服从 package 协议；无法判断时停止该条，不猜测。

## 五、`set` 的组成语义

### 包含单件

记录构成该装束身份的基础衣装单元，至少两个核心单元。某个单元不必另有独立 `CLO-*`；一个原生内衣或泳装单元内部有两个部件，也只算一个单元，不据此凑成 `set`。

### 必需层

记录使用该装束时不可缺少但未必承担外观识别的穿着层，例如必要内层、安全层或结构支撑层。不得为满足完整感虚构看不见的内层。

### 可选单件

记录不改变装束身份、但可随场景加入或移除的鞋履、外搭和配饰。

### 部件联动

每个 `set` 还要说明：

- 哪些颜色、纹样、边缘、系带或五金跨部件重复；
- 哪个部件承担主体焦点，哪些负责承接；
- 材质关系是统一、递进还是对比；
- 替换哪些部件会使其退化为普通搭配。

## 六、基础单元的搭配语义

### `搭配方式=standalone`

基础单元可作为主要可见主体独立成立，但仍可能需要基础内层或常规鞋履。

### `搭配方式=required`

缺少特定角色就无法形成可穿用或符合用途的方案。正文必须明确“必需角色”和约束。

### `搭配方式=optional`

基础单元可使用，但搭配特定部件会改变完整度、比例、风格或环境适配。

“搭配方式”描述基础单元的外部搭配需要；原生内衣或泳装已有的内部部件不重复列作外部必需角色，也不因此构成新的 `set`。

## 七、穿着层与组成检查

对每个实体按实际相关性检查：

| 层级 | 观察内容 |
|---|---|
| 贴身基础层 | 贴肤、承托、安全、透痕、肩带或闭合件外露 |
| 主体层 | 主要轮廓、比例、颜色、图案和身份识别 |
| 覆盖／外搭层 | 开合、体积、保暖、防护和动作限制 |
| 腿部层 | 覆盖终点、透明度、压缩、下滑、卷边和勾丝 |
| 足部层 | 重心、步态、抓地、稳定、路面和长时穿着 |
| 配饰层 | 焦点、身份、功能、重量、摆动、声音和勾挂风险 |

需要区分：

- **可见部件**：当前画面或档案确定存在；
- **必要内层**：穿用或结构必需，但不一定可见；
- **可选配件**：移除后不破坏核心身份；
- **设计建议**：项目为了角色或场景新增，不得混入来源事实。

## 八、结构描述最低维度

每个实体按实际对象说明：

- 具体款式；
- 廓形；
- 合体度、松量、支撑、压缩和塑形；
- 腰线、长度和身体锚点；
- 领口、肩背、袖型、腰胯、裤裙线或鞋面结构；
- 省道、分割线、拼片、褶裥、抽褶、斜裁、开衩等关键结构；
- 覆盖与露肤边界；
- 固定、闭合、调节、承重和系带；
- 穿脱顺序；
- 坐、立、行走、抬臂、弯腰、奔跑、涉水等相关动作；
- 上窜、下滑、卷边、走位、扭转、堆积、张口、勒痕等失效风险。

具体术语按 [服装术语与观察词典](服装术语与观察词典.md) 使用；看不清时写可证实的通俗描述。

## 九、季节与环境

- 季节只用春、夏、秋、冬的一个或多个明确值；
- 四季适用时写“春、夏、秋、冬”，不用“全年”；
- 室内恒温、空调环境、过渡季、雨季、海边、舞台强光等写在环境补充；
- 季节判断必须结合覆盖、厚薄、透气、保暖、内层和活动强度；
- 证据不足时写“未判定”及原因，不根据颜色或用途硬猜季节。

## 十、分类流程

```text
确认实际对象
  → 是否为一个基础衣装单元（独立衣物或原生配套内衣／泳装）
    → 是：判断独立维护价值
      → 成立：piece
        → 从 top / bottom / dress / jumpsuit / bodysuit / swimsuit /
           hosiery / footwear / accessory 中选择一个类型
      → 不成立：不建档
    → 否：是否至少有两个核心基础衣装单元
      → 是：判断是否具有不依赖当前场景的固有成套身份
        → 成立：set
        → 不成立：逐件判断 piece，整体只作临时搭配候选
      → 否：停止并重新确认实际对象
  → 判断主用途与兼容用途
  → 判断 piece 的单件类型或 set 的实际部件角色
  → 记录穿着层级、季节和结构
  → 普通组合只保留为临时搭配方向
```

最终检查：档案粒度、用途、九种基础单元类型和穿着层级必须分别成立；不得产出旧 `look`、冗余“组合形式”或本项目禁用的 `one-piece`。
