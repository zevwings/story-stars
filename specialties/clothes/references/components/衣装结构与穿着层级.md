# Story Stars 衣装结构与穿着层级

本文件是 Story Stars 项目唯一的衣装分类解释权，基于 Clothes Specialty `0.0.6` 的项目分类覆盖机制，定义成套装束、可复用单件和不落盘临时搭配的边界，并规定正文中的结构组成、单件类型和穿着层级。它不保存实际衣物，不分配 `CLO-*`。

## 一、五条独立判断轴

每份衣装档案分别判断以下各轴，不能用一个词替代其它轴。

### 1. 档案粒度

- `look`：由至少两个物理独立的核心部件共同构成、具有固有完整身份的成套装束。
- `piece`：一个物理独立的实际衣物／穿戴配饰；一件式衣物即使能独立完成全身造型，仍然是 `piece`。
- 临时搭配候选：若干 `piece` 为人物或场景临时组成的方案，不是第三种 `record_kind`，不进入 catalog。

### 2. 结构组成

只用于 `look`：

- `multi-piece`：多个物理独立部件因固有设计、结构语言、纹样、标识或角色／作品识别共同形成不可随意替换的装束身份。

本项目不新建分类表 `组合形式=single-piece`。旧档案或外部任务书出现该值时，只能作为待迁移输入；迁移后应归入相应的单件类型，不得继续作为有效 catalog 输出。

### 3. 单件类型

只用于 `piece`：

- `top`：上身主体、外搭或覆盖层，包括衬衫、胸衣式上装、背心、外套和罩衫。
- `bottom`：裙、裤、裙裤、围裹式下装。
- `dress`：没有分离裤腿结构、以裙摆为主体的一件式衣物，包括连衣裙、旗袍、单件礼服和睡裙。
- `jumpsuit`：上下身连续且具有两条分离裤腿结构的一件式衣物，包括连体裤、连身工装和 romper。
- `bodysuit`：上下身连续、没有独立裙摆或分离长裤腿的一件式贴体衣物，包括连体紧身衣、时装 body、体操服和物理上不可拆分的单件 COS 主体。
- `swimsuit`：一个物理独立的一件式泳装主体；成套比基尼不归入此类型。
- `hosiery`：丝袜、连裤袜、长袜、短袜和腿套。
- `footwear`：鞋、靴、凉鞋和拖鞋。
- `accessory`：首饰、腰带、手套、帽、发饰、包、披肩及其它穿戴配件。

不新增 `one-piece`、`other`、`outerwear`、`underwear`、`suit` 等分类表枚举。更细类别写在正文描述中。

### 4. 用途

`primary_use` 只能有一个：

- `daily`
- `stage`
- `ceremonial`
- `intimate`
- `sport`
- `swimwear`
- `action`
- `cos`

其它合理用途进入 `compatible_uses`。同一实体不得因用途不同复制到多个目录。

用途不能替代结构分类，也不新增 `tags` 或复合枚举。典型交叉判例如下：

| 实际对象 | `record_kind` | 结构字段 | 用途字段 | catalog 目录 |
|---|---|---|---|---|
| 一个物理独立的情趣短裙／半裙 | `piece` | `单件类型=bottom` | `主要用途=intimate` | `catalog/pieces/bottom/` |
| 一件式情趣连衣裙／睡裙 | `piece` | `单件类型=dress` | `主要用途=intimate` | `catalog/pieces/dress/` |
| 原生固定的情趣上衣＋短裙套组 | `look` | `组合形式=multi-piece` | `主要用途=intimate` | `catalog/looks/intimate/` |
| 本质为日常裙装，只能兼用于私密场景 | `piece` | 按实际结构选择 `bottom` 或 `dress` | `primary_use: daily`，`compatible_uses` 包含 `intimate` | 对应 `piece_type` 目录 |

短、透、露肤多或带蕾丝不自动等于 `intimate`；以设计的主要穿用目的和档案证据判断。`piece` 始终按物理结构进入九种单件目录，只有符合多件套准入的装束才按用途进入 `catalog/looks/`。

### 5. 穿着层级

穿着层级只写正文，不新增 schema：

- 贴身基础层；
- 主体层；
- 覆盖／外搭层；
- 腿部层；
- 足部层；
- 点睛／功能配饰层。

同一件衣物在不同场景可能承担不同层级，但其实际结构身份不因此改变。

## 二、`look` 的严格准入

### 可以作为 `look`

- 完整 COS、制服、西装套装、礼服套装、舞台套装、成套私密装束或固定泳装套组，并且至少有两个物理独立的核心服装部件；
- 多个部件共享稳定纹样、配色、边缘、五金、标识或角色识别；
- 拆开或替换关键部件后，原装束身份消失，而不只是风格略有变化；
- 档案能够自足说明其固有组成，不需要设计者临时补完关键部件。

### 不得作为 `look`

- 连衣裙、旗袍、单件礼服、睡裙、连体裤、连体紧身衣、一件式泳装或物理上不可拆分的单件 COS 主体；
- 吊带上衣＋牛仔短裤；
- 衬衫＋半裙；
- 针织衫＋长裤；
- 普通泳衣临时搭罩衫、拖鞋和草帽；
- 任何只因比例、配色、场合或模特表现得好看而成立的普通单品组合。

“图片里东西很多”“搭好后能直接出门”“上下装在这张图中缺一不可”都不是 `multi-piece look` 的充分条件。

### 原生套装与分件

- 来源本身就是稳定套装时，直接建立一个 `look`，不要求先把全部部件拆成 `piece` 再合并。
- 只有确实会被跨造型独立检索、替换和复用的部件，才额外建立自己的 `piece` 档案；未独立建档的部件仍可完整写在 `included_pieces`。
- 同一来源既形成 `look` 又形成若干 `piece` 时，各实体必须拥有不同的 `CLO-*`，并明确它们的从属与复用关系。
- 不得为了追求“原子化”把一个不可拆分的衣物虚构成多个物理单件，也不得为了减少文件把真正独立的套装部件合写成一个 `piece`。

### 常见边界

- 西装外套、马甲属于 `top`，西裤或西装裙属于 `bottom`；具有固定面料、剪裁和成套身份的两件套／三件套可另建 `look`，但不新增 `suit` 类型或目录。
- 单件晚礼服、婚纱或宫廷长裙属于 `piece + dress`；只有礼服主体与斗篷、披肩、胸衣、外裙等至少两个物理独立核心部件共同形成稳定身份时，才是 `look`。
- 一件式泳衣属于 `piece + swimsuit`；固定比基尼上装与下装共同组成稳定商品／设计套组时，可建 `look + multi-piece`。普通罩衫、拖鞋、草帽的临时加入不使泳衣升级为 `look`。
- 可拆分比基尼部件若具有跨造型独立复用价值，可分别按其实际结构建 `top`／`bottom`；否则只记录为该 `look` 的内部部件。

### 判定问题

依次回答：

1. 对象是否至少包含两个物理独立的核心服装部件？若否，直接按 `piece` 判断。
2. 这本身是什么成套装束？
3. 是否具有不依赖当前模特和场景的稳定身份？
4. 多个部件是否共享不可随意替换的设计系统？
5. 替换关键部件后，是身份消失，还是只变成另一套普通搭配？
6. 是否还需要补一个关键服装决定才能使用？

如果答案只是“这些单件这一次怎样搭”，就不是 `look`。

## 三、`piece` 的建立门槛

只有同时具有实际对象和独立复用价值的单件才建立 `piece`：

- 有明确、可复述的结构身份；
- 能跨多个造型复用；
- 对比例、风格、张力或动作有独立贡献；
- 有稳定的搭配要求或禁忌；
- 能在不依赖原图的情况下自足描述；
- 未来 `$clothes-designer` 可以直接检索并使用。

不要因为图片里“看得到”就机械拆件。斜襟、吊带、鱼骨、花边、拉链等是结构或术语，不是天然独立的 `piece`。

## 四、来源材料与项目实体不是一一对应

一份来源材料允许形成：

- **零个实体**：没有足够证据，或没有任何值得独立维护的对象；
- **一个实体**：明确管理一个完整装束或一个主体单件；
- **多个实体**：普通组合中有多个真正可复用的单件；
- **合并候选**：多份来源材料可能描述同一实体，但必须先核验证据和 ID。

一个源 ID 不得复制给拆出的多个实体。ID 分配、冲突和状态服从 package 协议；无法判断时停止该条，不猜测。

## 五、`look` 的组成语义

### `included_pieces`

记录构成该装束身份的实际部件。某个部件不必另有独立 `CLO-*` 才能在此出现。

### `required_layers`

记录使用该装束时不可缺少但未必承担外观识别的穿着层，例如必要内层、安全层或结构支撑层。不得为满足完整感虚构看不见的内层。

### `optional_pieces`

记录不改变装束身份、但可随场景加入或移除的鞋履、外搭和配饰。

### 部件联动

每个 `multi-piece look` 还要说明：

- 哪些颜色、纹样、边缘、系带或五金跨部件重复；
- 哪个部件承担主体焦点，哪些负责承接；
- 材质关系是统一、递进还是对比；
- 替换哪些部件会使其退化为普通搭配。

## 六、单件的搭配语义

### `pairing: standalone`

单件可作为主要可见主体独立成立，但仍可能需要基础内层或常规鞋履。

### `pairing: required`

缺少特定角色就无法形成可穿用或符合用途的方案。正文必须明确 `required_roles` 和约束。

### `pairing: optional`

单件可使用，但搭配特定部件会改变完整度、比例、风格或环境适配。

`pairing` 描述单件的搭配需要，不表示多个单件已经构成新的 `look`。

## 七、穿着层与组成检查

对每个实体按实际相关性检查：

| 层级 | 观察内容 |
|---|---|
| 贴身基础层 | 贴肤、承托、安全、透痕、肩带或闭合件外露 |
| 主体层 | 主要轮廓、比例、颜色、图案和身份识别 |
| 覆盖／外搭层 | 开合、体积、保暖、防护和动作限制 |
| 腿部层 | 覆盖终点、透明度、压缩、下滑、卷边和勾丝 |
| 足部层 | 重心、步态、抓地、稳定、路面和长时穿着 |
| 配饰层 | 焦点、身份、功能、重量、摆动、声音和勾挂风险 |

需要区分：

- **可见部件**：当前画面或档案确定存在；
- **必要内层**：穿用或结构必需，但不一定可见；
- **可选配件**：移除后不破坏核心身份；
- **设计建议**：项目为了角色或场景新增，不得混入来源事实。

## 八、结构描述最低维度

每个实体按实际对象说明：

- 具体款式；
- 廓形；
- 合体度、松量、支撑、压缩和塑形；
- 腰线、长度和身体锚点；
- 领口、肩背、袖型、腰胯、裤裙线或鞋面结构；
- 省道、分割线、拼片、褶裥、抽褶、斜裁、开衩等关键结构；
- 覆盖与露肤边界；
- 固定、闭合、调节、承重和系带；
- 穿脱顺序；
- 坐、立、行走、抬臂、弯腰、奔跑、涉水等相关动作；
- 上窜、下滑、卷边、走位、扭转、堆积、张口、勒痕等失效风险。

具体术语按 [服装术语与观察词典](服装术语与观察词典.md) 使用；看不清时写可证实的通俗描述。

## 九、季节与环境

- 季节只用春、夏、秋、冬的一个或多个明确值；
- 四季适用时写“春、夏、秋、冬”，不用“全年”；
- 室内恒温、空调环境、过渡季、雨季、海边、舞台强光等写在环境补充；
- 季节判断必须结合覆盖、厚薄、透气、保暖、内层和活动强度；
- 证据不足时写“未判定”及原因，不根据颜色或用途硬猜季节。

## 十、分类流程

```text
确认实际对象
  → 是否为一个物理独立的衣物／穿戴配饰
    → 是：判断独立维护价值
      → 成立：piece
        → 从 top / bottom / dress / jumpsuit / bodysuit / swimsuit /
           hosiery / footwear / accessory 中选择一个类型
      → 不成立：不建档
    → 否：是否至少有两个物理独立的核心服装部件
      → 是：判断是否具有不依赖当前场景的固有成套身份
        → 成立：look + multi-piece
        → 不成立：逐件判断 piece，整体只作临时搭配候选
      → 否：停止并重新确认实际对象
  → 判断主用途与兼容用途
  → 判断单件类型或 look 的实际部件角色
  → 记录穿着层级、季节和结构
  → 普通组合只保留为临时搭配方向
```

最终检查：档案粒度、项目有效结构组成、用途、九种单件类型和穿着层级必须分别成立；不得产出本项目已经禁用的 `single-piece` 或 `one-piece`。
