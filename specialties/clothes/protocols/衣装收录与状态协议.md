# 衣装收录与状态协议

## 写入门禁

只有作者明确要求“收录”“建档”“更新 CLO”“拆成项目组件”或目录查重时才写项目参考。写入前必须确认 `$CLOTHES_ROOT` ready；未配置、禁用、缺包、版本冲突或其它 blocking 状态全部停止目录操作。

## 稳定 ID

- ID 使用 `CLO-0001` 形式，不编码用途、部件类型或名称。
- 文件名使用 `CLO-0001_名称.md`；名称变化不改变 ID。
- 分配新编号必须运行 `sw specialty reserve-id clothes --root "$STORY_PROJECT_ROOT"`。命令在项目锁内同时扫描 `references/catalog/` 与 `.sw/reservations/clothes/`，并以 `create_new` 原子写入 reservation；不得绕过 reservation 自行取最大值。
- 发现重复 ID、同一 ID 多实体或同一实体多分类时停止，不自动覆盖或合并。

## 版本化 frontmatter

```yaml
---
schema: clothes.catalog@1
id: CLO-0001
record_kind: piece
status: reference_only
---
```

只允许上述四个字段。`schema` 固定为 `clothes.catalog@1`；`id` 用于去重和索引；`record_kind` 只允许 `look | piece`，并决定正文语法；`status` 只允许 `reference_only | analyzed | adapting | candidate_ready | retired`，并决定参考工作流门禁。分类、搭配、用途、组成和正式去向必须写在 Markdown 正文，不得再写入 frontmatter。

`0.0.6` 是硬切换：不读取、不生成、不兼容旧版 `composition`、`piece_type`、`pairing`、`primary_use`、`compatible_uses`、`included_pieces`、`required_layers`、`optional_pieces`、`pairing_requirements` 或 `formal_targets` frontmatter。发现任一旧字段必须停止，由人工将其迁移到本协议的 Markdown 结构。

## Markdown 结构

每个档案必须且只能有一个 H1，且 H1 必须位于所有 H2 之前。文件名中的 ID、frontmatter `id` 和 H1 中的 ID 必须一致。正文不得保留 `<...>` 占位符、空列表标记或未声明结构。

### 通用分类表

第一个 H2 固定为 `## 分类`，只允许一张两列表：

```md
## 分类

| 字段 | 值 |
| --- | --- |
| 组合形式 | multi-piece |
| 主要用途 | ceremonial |
| 兼容用途 | stage、daily |
```

- `look` 必须使用 `组合形式`、`主要用途`，可选 `兼容用途`。`组合形式` 为 `single-piece | multi-piece`。
- `piece` 必须使用 `单件类型`、`搭配方式`、`主要用途`，可选 `兼容用途`。`搭配方式` 为 `standalone | required | optional`。
- `主要用途` 和 `兼容用途` 只允许 `cos | daily | stage | ceremonial | intimate | sport | swimwear | action`；多值使用中文顿号 `、` 分隔。没有兼容用途时省略整行，不写空值。
- 表头、字段名与行数必须符合当前 `record_kind`；禁止额外行、额外表格或表格外说明文字。

### `look` 正文

`分类` 后按顺序使用：

1. `## 组成`：必须包含 `### 包含单件`；有实际内容时可增加 `### 必需层` 和 `### 可选单件`。每个小节只允许一个非空列表。
2. `## 来源与边界`：自足区分观察、作者确认和设计推断。
3. `## 结构与使用`：说明颜色、材质、轮廓、固定、穿脱与活动条件。
4. `## 使用条件与叙事作用`：说明环境、功能与叙事用途。

### `piece` 正文

`分类` 后按顺序使用：

1. `## 搭配要求`：按需使用 `### 必需角色`、`### 可选角色`、`### 约束`，每个小节只允许一个非空列表。`搭配方式=required` 时必须有 `必需角色`；三个小节都无内容时省略整个 H2。
2. `## 来源与边界`。
3. `## 结构与使用`。
4. `## 使用条件与叙事作用`。

当 `主要用途` 或 `兼容用途` 包含 `intimate` 时，上述固定结构之后必须增加 `## 张力与互动语法`。已经自足转写到正式 owner 时，最后增加 `## 正式去向`，只允许一个非空、不重复的项目相对路径列表。正式去向与 `status` 正交：它可以出现在任一非 `retired` 状态，是否已采用只由该节派生，不再存储 `transferred` 等第二个状态。除本节列出的 H2/H3 外，不得自造新的结构标题。

## 项目分类覆盖

通用默认分类如下：

- `组合形式`: `single-piece | multi-piece`；
- `单件类型`: `top | bottom | one-piece | hosiery | footwear | accessory`。

项目可以在 `references/components/_index.md` 中指定一个分类权威文件，并由该文件：

1. 用一个项目封闭枚举替换默认 `单件类型`；
2. 将 `组合形式` 的实际输出收窄为默认枚举的子集；
3. 规定 `catalog/looks/` 与 `catalog/pieces/` 的项目目录和索引映射；
4. 给出项目特有的边界判例与迁移规则。

项目覆盖不得新增 `record_kind`、`组合形式` 值、用途、状态、frontmatter 字段或 Markdown 结构标题。覆盖生效后，同一 catalog 必须统一使用项目枚举，目录、分类表和索引必须一致；不得同时生成默认类型与项目替代类型。项目没有声明覆盖时使用通用默认分类。分类权威缺失、重复、互相矛盾或目标无法归类时停止该条收录。

## `intimate` 附加内容

当分类表的 `主要用途` 或 `兼容用途` 包含 `intimate` 时，档案正文必须增加“张力与互动语法”，至少说明：

- 核心张力与主要材质反馈；
- 一条主导互动路径，例如隔料抚摸、缓慢褪下、保留穿着或一次性撕裂；
- 互动后的衣物结果：完整、位移、脱下或损耗；
- 撕裂若成立，具体可损耗分件、预设薄弱点、皮肤保护和替换／报废条件；若不成立，明确不以撕裂实现张力；
- 本档只描述衣物可承载的设计路径，不替人物建立稳定偏好，不替任何场次决定实际动作。

同一档案可以说明一条主路径和一条克制的替代路径，但不得机械罗列所有动作。丝袜、蕾丝、系带等材质或结构不自动等于撕裂、束缚或服从。

## 状态

- `reference_only`：保存了可回查参考，尚未完成结构分析。
- `analyzed`：完成拆解，尚未进入具体适配。
- `adapting`：正在为人物或场景改造。
- `candidate_ready`：候选规格完整，可直接用于后续适配或再次转写；是否已有正式 owner 仍由正式去向独立表示。
- `retired`：不再活跃采用，保留去重、避错或历史价值。

状态只表示参考工作流，不表示故事事实。是否已采用由实际存在且通过核验的 `## 正式去向` 派生；删除最后一个正式去向后，采用结果自然回到未采用，不需要同步改第二个状态。迁移旧档时，`transferred` 统一按原工作进度映射到 `candidate_ready`，并只在正式 owner 确实存在且自足时保留其目标路径。
