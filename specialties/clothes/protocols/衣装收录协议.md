# 衣装收录协议

## 写入门禁

外部素材到 catalog 的创建、查重和结构拆解由 `clothes-decomposer` 负责；人物选择、适配与正式去向由 `clothes-designer` 负责。只有作者明确要求“收录”“建档”“更新 CLO”“拆成项目组件”或目录查重时才写项目参考。写入前必须确认 `$CLOTHES_ROOT` ready；未配置、禁用、缺包、版本冲突或其它 blocking 状态全部停止目录操作。

两个 Skill 不得互相越权：`clothes-decomposer` 不写人物 owner；`clothes-designer` 不从外部素材创建新 `CLO-*`。需要完整闭环时按两个 Skill 顺序执行，并分别满足各自写入授权。

catalog 是完成结构拆解、可直接复用且通过当前协议校验的参考集合。只保存来源、证据不足、结构尚未闭合或仍有占位符的材料不得分配 `CLO-*`，应继续留在原始素材、当前会话候选或 `.analysis`。人物适配中的临时进度也不写回 catalog。

## 稳定 ID

- ID 使用 `CLO-00001` 形式，不编码用途、部件类型或名称。
- 文件名使用 `CLO-00001_名称.md`；名称变化不改变 ID。
- 分配新编号必须运行 `sw specialty reserve-id clothes --root "$STORY_PROJECT_ROOT"`。命令在项目锁内同时扫描 `references/catalog/` 与 `.sw/reservations/clothes/`，并以 `create_new` 原子写入 reservation；不得绕过 reservation 自行取最大值。
- 发现重复 ID、同一 ID 多实体或同一实体多分类时停止，不自动覆盖或合并。

## 版本化 frontmatter

```yaml
---
schema: clothes.catalog@2
id: CLO-00001
record_kind: piece
---
```

只允许上述三个字段。`schema` 使用 schema registry 为 `clothes.catalog` 登记的当前版本；`id` 用于去重和索引；`record_kind` 只允许 `set | piece`，并决定正文语法。分类、搭配、用途、组成和正式去向必须写在 Markdown 正文，不得写入 frontmatter。

这是硬切换：旧 schema、`record_kind=look`、`catalog/looks/`、任何 `status` 字段以及旧业务 frontmatter 都是非法输入，当前 Skill 不读取、不生成、不提供默认值或映射。迁移时保留稳定 `CLO-*` 和经核验的正式去向；将稳定多件套组迁为 `set`，将物理单件迁为 `piece`，并把目录改为 `catalog/sets/` 或 `catalog/pieces/`。

## Markdown 结构

每个档案必须且只能有一个 H1，且 H1 必须位于所有 H2 之前。文件名中的 ID、frontmatter `id` 和 H1 中的 ID 必须一致。正文不得保留 `<...>` 占位符、空列表标记或未声明结构。

### 通用分类表

第一个 H2 固定为 `## 分类`，只允许一张两列表：

```md
## 分类

| 字段 | 值 |
| --- | --- |
| 主要用途 | ceremonial |
| 兼容用途 | stage、daily |
```

- `set` 必须使用 `主要用途`，可选 `兼容用途`。`set` 天然由至少两个物理独立核心分件构成，不再存储冗余的“组合形式”。
- `piece` 必须使用 `单件类型`、`搭配方式`、`主要用途`，可选 `兼容用途`。`搭配方式` 为 `standalone | required | optional`。
- `主要用途` 和 `兼容用途` 只允许 `cos | daily | stage | ceremonial | intimate | sport | swimwear | action`；多值使用中文顿号 `、` 分隔。没有兼容用途时省略整行，不写空值。
- 表头、字段名与行数必须符合当前 `record_kind`；禁止额外行、额外表格或表格外说明文字。

### `set` 正文

`分类` 后按顺序使用：

1. `## 组成`：必须包含 `### 包含单件`，且至少列出两个物理独立核心衣物或穿戴配饰；有实际内容时可增加 `### 必需层` 和 `### 可选单件`。`必需层` 表示真实穿用时不可缺少但不属于套组固有身份的角色，`可选单件` 表示移除后不破坏套组身份的扩展。每个小节只允许一个非空列表。
2. `## 来源与边界`：自足区分观察、作者确认和设计推断。
3. `## 结构与使用`：说明颜色、材质、轮廓、固定、穿脱与活动条件。
4. `## 使用条件与叙事作用`：说明环境、功能与叙事用途。

### `piece` 正文

`分类` 后按顺序使用：

1. `## 搭配要求`：按需使用 `### 必需角色`、`### 可选角色`、`### 约束`，每个小节只允许一个非空列表。`搭配方式=required` 时必须有 `必需角色`；三个小节都无内容时省略整个 H2。
2. `## 来源与边界`。
3. `## 结构与使用`。
4. `## 使用条件与叙事作用`。

当 `主要用途` 或 `兼容用途` 包含 `intimate` 时，上述固定结构之后必须增加 `## 张力与互动语法`。已经自足转写到正式 owner 时，最后增加 `## 正式去向`，只允许一个非空、不重复的项目相对路径列表。是否已采用只由该节及实际 owner 校验结果派生；catalog 不保存第二份工作流或采用状态。除本节列出的 H2/H3 外，不得自造新的结构标题。

## 项目分类覆盖

通用默认分类只定义 `piece` 的 `单件类型`: `top | bottom | one-piece | hosiery | footwear | accessory`。

项目可以在 `references/components/_index.md` 中指定一个分类权威文件，并由该文件：

1. 用一个项目封闭枚举替换默认 `单件类型`；
2. 规定 `catalog/sets/` 按主要用途、`catalog/pieces/` 按单件类型组织的项目目录和索引映射；
3. 给出项目特有的 `set`／`piece` 边界判例与迁移规则。

项目覆盖不得新增 `record_kind`、用途、frontmatter 字段或 Markdown 结构标题，也不得重新引入“组合形式”。覆盖生效后，同一 catalog 必须统一使用项目枚举，目录、分类表和索引必须一致；不得同时生成默认类型与项目替代类型。项目没有声明覆盖时使用通用默认分类。分类权威缺失、重复、互相矛盾或目标无法归类时停止该条收录。

## `intimate` 附加内容

当分类表的 `主要用途` 或 `兼容用途` 包含 `intimate` 时，档案正文必须增加“张力与互动语法”，至少说明：

- 核心张力与主要材质反馈；
- 一条主导互动路径，例如隔料抚摸、缓慢褪下、保留穿着或一次性撕裂；
- 互动后的衣物结果：完整、位移、脱下或损耗；
- 撕裂若成立，具体可损耗分件、预设薄弱点、皮肤保护和替换／报废条件；若不成立，明确不以撕裂实现张力；
- 本档只描述衣物可承载的设计路径，不替人物建立稳定偏好，不替任何场次决定实际动作。

同一档案可以说明一条主路径和一条克制的替代路径，但不得机械罗列所有动作。丝袜、蕾丝、系带等材质或结构不自动等于撕裂、束缚或服从。

## 完成不变量

- catalog 中每个 `CLO-*` 都必须符合 schema registry 当前登记的 `clothes.catalog` 契约并通过 validator；存在本身即表示结构拆解完成、可用于后续选择和适配。
- 不完整素材、未闭合结构和纯来源占位不得进入 catalog，也不得借新增字段表达进度。
- 人物适配进度保留在当前会话或候选设计中；只有人物 owner 与索引验证成功后，才追加 `## 正式去向`。
- 需要停用某条错误或失效记录时，删除或移出 catalog 前先核对引用并按项目变更流程处理；不得用状态字段把无效记录继续伪装为有效 catalog。
