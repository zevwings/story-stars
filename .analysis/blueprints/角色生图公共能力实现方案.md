# 角色生图公共能力实现方案

> **文档状态**：已确认目标与边界下的实施蓝图，不是故事正典，也不代表代码已经实现。
>
> **实施目标**：在公共 `story-writer` 中建立题材中立的角色生图能力，最终只服务三个结果：图片漂亮、同一角色脸型稳定、同一角色可以稳定复现多套服装。
>
> **真源边界**：人物事实仍以项目 [`BIBLE.md`](../../BIBLE.md)、[`characters/`](../../characters/_index.md) 及具体人物卡为准；本文只描述公共能力如何读取这些真源、调用生图服务并管理视觉生产资产。与正式人物卡冲突时，服从正式人物卡。
>
> **原型来源**：现有 [`zevwings/intimacy-visuals`](https://github.com/zevwings/intimacy-visuals) 只作为实现经验与资产原型，不直接整体并入 `story-writer`。

## 一、最终目标

角色生图系统只解决以下三件事：

1. **图片漂亮**：画风、光影、构图、质感和完成度达到作者愿意直接保留使用的水平。
2. **脸型稳定**：同一角色跨姿态、镜头、场景和服装时仍可识别为同一个人，不与其他角色撞脸。
3. **多套服装稳定**：每套已批准服装可以跨场景复现，不因更换姿势、镜头或背景而重设计。

系统不以提示词文档数量、规则数量、候选图数量或自动化步骤数量作为成功标准。所有结构只服务最终图片结果。

### 1.1 非目标

第一版不做以下事项：

- 不把 `intimacy-visuals` 整仓并入公共 runtime；
- 不建立通用服装分类库或画风分类库；
- 不先训练角色 LoRA；
- 不先做 UI；
- 不把地图、剧情线图、图标等其它视觉能力混入角色生图；
- 不承诺无人审核的绝对一致性；
- 不把 prompt 通过、请求成功或文件保存成功等同于图片合格。

## 二、已确认的硬边界

### 2.1 自动生图资格

只有同时满足以下条件的角色，才允许进入自动生图：

- 已在项目人物索引登记；
- 存在 `主卡.md`；
- 存在 `形象.md`；
- 存在 `衣装.md`。

执行门禁固定为：

```text
解析角色
→ 检查主卡、形象、衣装
→ 任一缺失：停止
→ 三卡齐全：编译视觉规格
→ 调用生图
```

明确禁止：

- 不根据主卡猜测缺失外貌；
- 不根据用户临时描述绕过 `形象.md` 或 `衣装.md`；
- 不用旧图代替缺失的正式人物卡；
- 不为缺卡角色自动生成 visual draft；
- 不自动调用 `character-builder` 补卡；
- 不因角色位于 `major`、`minor` 或 `preentry` 而改变门禁。

若角色曾有视觉资产，后来缺失或删除 `形象.md`、`衣装.md`：

- 旧图仍可查看；
- identity/outfit pack 标记为 `stale`；
- 禁止继续自动生成新图。

### 2.2 公共层不预设题材内容

公共 `story-writer` 不内置：

- 日常装、礼服、战斗服、睡衣等服装类型枚举；
- 仙侠、现代、科幻、二次元、写实等画风枚举；
- 固定八态、仙古／凡尘、职业制服等项目语义；
- 具体角色、服装名称、场景名称或项目资产。

公共层只定义“如何描述、生成、验证和批准一套服装”。具体 `outfit_id`、画风和参考图全部由项目自行提供。

### 2.3 不反写人物正典

- 生图 Skill 只读 `characters/`；
- 模型补出的细节不自动成为人物事实；
- 批准图片只成为视觉生产参考，不自动更新 `形象.md` 或 `衣装.md`；
- 作者明确要求修改人物正式设定时，转交 `character-builder`；
- 不建立 `runtime/profiles/<角色>/视觉.md`、`脸部.md`、`身体.md`、`衣装.md` 等人物镜像层。

## 三、总体分层

| 层级 | 位置 | 职责 | 真源性质 |
| --- | --- | --- | --- |
| 人物正式层 | `characters/<层级>/<角色>/` | 主卡、形象、衣装及项目专属静态卡 | 故事正式真源 |
| 项目视觉生产层 | `visuals/` | 已批准的身份、服装、画风参考包 | 项目视觉生产基准，不是故事正典 |
| 运行层 | `.story-visuals/` | job、run、候选图、QC、重试和审核记录 | 可再生运行产物 |
| 公共方法层 | `story-writer/skills/` | 触发、流程、读取声明、冲突判断、人工选择 | 公共 Agent 方法 |
| 确定性工具层 | `story-writer/tools/` | 真源解析、hash、job、provider、状态机、QC | 公共可执行工具 |
| 模型服务层 | 外部 provider | 实际图片生成、编辑、局部修复 | 外置依赖 |

核心关系：

```text
characters/*.md
  决定这个人是谁、长什么样、稳定审美是什么

identity / outfit / style packs
  决定模型实际看到哪些已批准参考图

character-visualizer + sw visual
  把人物真源、参考资产与本次场景编译为生成任务
```

## 四、Skill 设计

### 4.1 只新增一个 Skill

新增：

```text
story-writer/skills/character-visualizer/
```

不拆分以下独立 Skill：

- `face-locker`；
- `outfit-designer`；
- `prompt-builder`；
- `batch-generator`；
- `qc-reviewer`。

这些动作共享同一套人物真源、参考资产、job 和批准状态，拆开会重复读取并形成多套工作流。

现有 [`character-builder`](../../../story-writer/skills/character-builder/SKILL.md) 继续管理人物正式卡；`character-visualizer` 不代写人物真源。

### 4.2 Skill 触发范围

建议 description 覆盖：

```yaml
---
name: character-visualizer
description: 基于项目 characters/ 正式人物真源与已批准视觉参考生成、换装、修订和确认角色图片；用于角色生图、锁脸、建立身份参考、多套服装、指定服装场景图、修脸修衣服、批准候选。角色缺少主卡、形象或衣装时停止，不生成图片；输出目标为人物设定或人物卡时转交 character-builder。
---
```

### 4.3 Skill 内部模式

| 模式 | 作用 | 前置条件 |
| --- | --- | --- |
| `identity` | 建立或修订角色多视角身份参考 | 三卡齐全 |
| `outfit` | 建立一套自由命名的服装母版 | 三卡齐全、identity 已批准 |
| `render` | 使用指定身份、服装和画风生成场景图 | identity/outfit/style 可用 |
| `repair` | 局部修脸、衣装、手部或其他区域 | 原 run 和对应参考包可追溯 |
| `approve` | 作者选择候选并登记为生产参考 | 候选已通过必要检查 |

Skill 只负责：

- 判断用户意图属于哪种模式；
- 声明本次读取的正式文件和参考包；
- 从自由 Markdown 中提炼带出处的视觉约束；
- 发现本次要求与人物真源的冲突；
- 组织候选展示与作者选择；
- 在硬门禁失败时停止。

Skill 不负责：

- 临时拼接文件扫描命令；
- 自己计算 hash；
- 临时实现 provider 请求；
- 管理重试和状态转换；
- 自行复制、移动或晋级资产；
- 修改 `characters/`。

## 五、角色真源解析器

### 5.1 必须建立共享解析器

新增公共内部能力：

```text
CharacterTruthResolver
```

它供 characters RAG、`sw visual` 和后续其它人物能力共同调用，只负责：

- 确定角色是谁；
- 确定人物正式入口；
- 返回卡片职责、路径、状态和 hash；
- 报告缺失或歧义。

它不生成提示词、不提炼人物语义、不管理图片。

### 5.2 现有 characters RAG 的缺口

现有 [`rag/characters.rs`](../../../story-writer/apps/sw/src/rag/characters.rs) 可以复用项目根、忽略规则、相对路径和 fingerprint 等基础，但不能直接成为视觉解析器：

- 扫描逻辑固定假设 `characters/<分组>/<角色>/`；
- `[[characters.roots]].path` 没有完整成为唯一扫描真源；
- `static_cards` 只是文件名列表，不能区分主卡、形象和衣装的职责；
- 配置卡全部缺失时会退化为目录中第一份 Markdown；
- 查询允许包含匹配，可能出现歧义；
- 派生 `.rag` 可能过期，不能作为人物事实。

视觉生成不允许沿用“任意 Markdown 回退”和“模糊命中后选第一条”。

### 5.3 人物根配置

最终配置建议从纯 `static_cards` 列表收敛为职责映射：

```toml
[[characters.roots]]
path = "characters"
type = "character.static"

[characters.roots.cards]
main = "主卡.md"
appearance = "形象.md"
wardrobe = "衣装.md"
contract = "契约.md"
```

说明：

- `main`、`appearance`、`wardrobe` 是公共人物卡职责；
- 其它 key 可由项目自行增加；
- 视觉器不会无条件读取 `contract` 等附加卡；
- 配置只声明卡片职责，不声明人物事实或服装类型；
- 实施迁移时同步更新 setup 模板、配置校验、RAG 和接入项目，不长期维护 `static_cards` 与 `cards` 两套解析真源。

### 5.4 确定性解析顺序

```text
1. 解析 project root
2. 读取 .story.config.toml
3. 读取一个或多个人物 root
4. 从人物 _index.md 及分类索引取得正式主卡链接
5. 按项目 ID → 正式姓名 → 别名 → 明确相对路径精确匹配
6. 唯一命中后解析角色目录
7. 检查 main / appearance / wardrobe
8. 计算正式文件 hash
9. 返回 ResolvedCharacterTruth
```

目录扫描只用于检查“索引是否漏登、链接是否失效”，不能把未登记目录静默提升为正式角色。

项目 ID 不强制采用 `CHR-0000`；公共解析器接受项目索引已经使用的 ID，但不得假定现有编号天然唯一。当前 [`characters/_index.md`](../../characters/_index.md) 工作树中可见重复的 `M-19`，这只是一项需要修复或阻断的项目快照，不得进入公共代码。resolver 必须先校验 ID 唯一性；重复 ID 不得绑定视觉资产，必须返回冲突并要求修复索引或使用明确路径。若同一姓名或别名命中多个角色，同样必须停止。

### 5.5 解析输出

```json
{
  "ready": true,
  "canonical_id": "项目定义的稳定 ID",
  "canonical_name": "正式姓名",
  "aliases": [],
  "group": "项目定义的分组",
  "status": "项目索引状态",
  "registry_source": "characters/_index.md",
  "cards": {
    "main": {"path": ".../主卡.md", "sha256": "..."},
    "appearance": {"path": ".../形象.md", "sha256": "..."},
    "wardrobe": {"path": ".../衣装.md", "sha256": "..."},
    "extras": []
  },
  "missing": [],
  "warnings": []
}
```

门禁失败：

```json
{
  "ready": false,
  "reason": "visual_source_incomplete",
  "missing": ["形象.md", "衣装.md"]
}
```

其它必须稳定返回的失败码：

- `character_not_registered`；
- `character_ambiguous`；
- `character_id_conflict`；
- `main_card_missing`；
- `visual_source_incomplete`；
- `source_outside_project`；
- `source_conflict`。

## 六、从人物卡编译视觉规格

### 6.1 文件职责

| 文件 | 视觉器使用内容 | 不应提取的内容 |
| --- | --- | --- |
| `主卡.md` | 姓名、年龄边界、身份／职业／文化约束、身体语言、视觉相关禁区 | 与画面无关的完整剧情、关系推进、能力流程 |
| `形象.md` | 脸型、五官、肤色、发型、身形、体态、识别锚点、禁止漂移 | 把意象误当成实际特效 |
| `衣装.md` | 稳定色彩、轮廓、材质、妆造、配饰、职业文化边界、禁区 | 把场景分类当成固定服装库存 |

### 6.2 不硬编码 Markdown 标题

人物模板提供公共结构，但项目可以自由扩写。实际人物卡可能使用“总体形象口径”“三个辨识锚点”“审美基因”“场景衣柜”等标题。

因此：

- CLI 只确定性收集原文、路径和 hash；
- Skill 负责语义提炼；
- 不按固定标题丢弃未识别内容；
- 不把整份人物卡直接拼入图片 prompt。

### 6.3 编译结果

每条视觉约束归入以下四类：

```text
required     必须保持
preferred    稳定审美倾向
forbidden    禁止出现或禁止漂移
unspecified  正式真源没有规定，本轮也不得伪称为既有事实
```

每条提炼结果必须携带：

- source path；
- source hash；
- heading 或短 snippet；
- 约束级别；
- 适用范围：identity / outfit / scene。

这份编译结果是可再生的 `render-spec`，不是新的角色知识库。

## 七、视觉生产资产协议

### 7.1 Identity Pack

身份参考包至少记录：

```toml
schema_version = 1
character_id = "项目角色 ID"
version = 1
status = "draft" # draft | approved | superseded | stale

required_anchors = []
forbidden_drifts = []

[[sources]]
path = "characters/.../形象.md"
sha256 = "..."

[[references]]
path = "refs/front.png"
sha256 = "..."
view = "front"
```

参考视角使用题材中立的技术词：

- `front`；
- `three_quarter_left`；
- `three_quarter_right`；
- `profile_left`；
- `profile_right`；
- `full_body`。

多格角色参考板可以保留作展示，但不得继续作为唯一模型输入。正式 identity pack 应保存独立多视角图片。

### 7.2 Outfit Pack

每套衣服使用项目自由定义的 `outfit_id`：

```toml
schema_version = 1
character_id = "项目角色 ID"
outfit_id = "项目自由命名"
version = 1
status = "draft"

required_features = []
forbidden_features = []

[[sources]]
path = "characters/.../衣装.md"
sha256 = "..."

[[references]]
path = "refs/front.png"
sha256 = "..."
view = "front"
```

建议参考视角：

- `front`；
- `back`；
- `side`；
- `detail`。

公共协议不限制 outfit 名称，也不维护项目衣柜枚举。

### 7.3 Style Pack

“漂亮”不能只靠通用提示词，需要项目批准的画风基准：

```toml
schema_version = 1
style_id = "项目自由命名"
version = 1
status = "approved"
positive = []
negative = []
```

style pack 保存项目自己的画风、质感、光影和构图参考；公共层不提供仙侠、现代、写实或二次元默认枚举。

项目 `STYLE.md` 是小说文风真源，不自动成为图片画风真源。图片画风只来自项目显式批准的 style pack；若项目希望参考 `STYLE.md`，必须在 style pack 来源中明确登记，而不是由公共工具自行推断。

### 7.4 Render Spec

单次生成使用派生规格：

```toml
character_id = "..."
identity_pack = "..."
outfit_pack = "..."
style_pack = "..."
scene_brief = "..."
aspect_ratio = "..."
candidate_count = 4
```

render spec 必须展开三类参考包的 required/forbidden 约束，并记录所有 source/ref hash。

### 7.5 Run Manifest

每次调用至少记录：

- `run_id`；
- `spec_hash`；
- provider；
- model snapshot；
- size、quality、seed 等实际参数；
- 所有参考图 hash；
- prompt hash；
- provider request id；
- 输出图 hash；
- QC 结果；
- 人工审核结果；
- 状态。

状态固定区分：

```text
prepared
→ generated
→ verified
→ accepted / rejected
```

`generated` 只表示取得图片文件，不表示图片合格。

## 八、项目目录

```text
visuals/
  styles/<style-id>/<version>/
    pack.toml
    refs/

  characters/<character-id>/
    identity/<version>/
      pack.toml
      refs/

    outfits/<outfit-id>/<version>/
      pack.toml
      refs/

.story-visuals/
  jobs/<job-id>/
  runs/<run-id>/
    render-spec.toml
    prompt.txt
    candidates/
    review.toml
  cache/
```

边界：

- `visuals/` 保存项目批准的稳定生产资产；
- `.story-visuals/` 保存可删除的运行产物；
- 大图不继续直接堆入普通 Git，实施前选择 Git LFS 或对象存储；
- manifest 应版本化；二进制存储方式可以独立替换。
- provider token、endpoint 和私有模型路径只进入用户级配置或环境变量，不写入项目 manifest、人物卡或公共 Skill。

## 九、生成流程

### 9.1 建立身份参考

```text
inspect 三卡门禁
→ 编译 identity 约束
→ 输入独立正脸、左右 45°、侧脸和全身参考
→ 生成多候选
→ 身份检查与跨角色防撞
→ 作者批准
→ identity pack approved
```

### 9.2 建立服装母版

```text
读取 approved identity pack
→ 读取衣装稳定语法
→ 接收项目自由命名 outfit brief
→ 在中性背景和标准姿态生成服装正背侧参考
→ 检查轮廓、层次、颜色、材质和配件
→ 作者批准
→ outfit pack approved
```

具体服装不会因为出现一次就自动写回 `衣装.md`。只有作者另外确认它已经成为人物跨场稳定事实时，才转交 `character-builder`。

### 9.3 生成场景图

```text
identity pack
+ outfit pack
+ style pack
+ 本次 scene brief
→ 多参考生成
→ 多候选
→ 身份、服装、构图与技术检查
→ 作者选择
```

场景生成只改变姿态、镜头、场景和光线，不重新设计脸与指定服装。

### 9.4 局部修复

- 脸漂只修脸；
- 衣装缺件只修衣装区域；
- 手部错误只修手部；
- 局部问题不默认整张重绘；
- 修复后的图片保留父图 lineage。

## 十、CLI 设计

第一版只提供一个公共入口：

```text
sw visual inspect <角色>
sw visual prepare <角色> --kind identity|outfit|render|repair
sw visual render <job-id>
sw visual verify <run-id>
sw visual approve <candidate-id>
```

### 10.1 `inspect`

- 精确解析角色；
- 返回人物索引、三卡路径与 hash；
- 检查 `ready`；
- 展示可用 identity/outfit/style packs；
- 不生成图片。

### 10.2 `prepare`

- 拒绝 `ready=false` 的角色；
- 生成不可变 job；
- 固定 source/ref hash；
- 检查所选 pack 状态；
- 生成 dry-run 预览。

### 10.3 `render`

- 按 adapter 能力构造请求；
- 上传多张身份、服装和画风参考；
- 保存 provider 实际参数和响应；
- 失败按原因重试，不静默丢弃不支持的控制项。

### 10.4 `verify`

- 技术检查；
- 身份一致性检查；
- 服装必需／禁止属性检查；
- 构图、身体和手部检查；
- 输出可解释的通过项与失败项。

### 10.5 `approve`

- 只接受明确 candidate id；
- 登记批准版本、hash、来源 job 和审核信息；
- 不修改 `characters/`；
- source hash 变化后将相关 pack 标记为 `stale`。

第一版不先扩 MCP。现有 MCP 主要提供公共资源读取，生成链先通过 CLI 完成。

## 十一、Provider Adapter

公共请求至少支持：

```text
identity_refs[]
outfit_refs[]
style_refs[]
pose_ref?
mask?
scene_brief
output_size
quality
candidate_count
```

adapter 必须显式声明能力：

```text
multi_reference
mask
seed
negative_prompt
identity_conditioning
outfit_conditioning
pose_control
lora
```

不支持的能力必须报错或明确降级，不能静默忽略。

第一阶段可先实现一个支持多参考图片的云端 adapter，验证完整闭环；若项目基准证明脸或服装仍不稳定，再加入更强身份、姿态或服装控制后端。模型和权重不打包进 `story-writer`。

## 十二、质量门禁

### 12.1 结构门禁

- 人物已登记；
- 三卡齐全；
- source/ref hash 有效；
- identity/outfit/style pack 状态满足本次操作；
- adapter 支持本次请求要求。

### 12.2 技术门禁

- 文件可读；
- 尺寸和格式正确；
- 目标人数正确；
- 无 provider 错误；
- 输出与 run manifest 一一对应。

### 12.3 身份门禁

- 与本人多视角参考保持一致；
- 必需面部锚点可见时必须正确；
- 与项目中最相近角色保持区分；
- 摄像角度遮挡某个锚点时，不把“不可见”误判成“缺失”。

### 12.4 服装门禁

- 必需轮廓、层次、主色、材质与配件逐项检查；
- 禁止部件不得出现；
- 服装母版与场景图的结构保持一致；
- 画风和场景不能覆盖服装硬属性。

### 12.5 审美门禁

“漂亮”最终由作者选择，不假装完全自动量化。自动检查只负责淘汰明显失败图；作者批准仍是 `accepted` 的唯一入口。

初期先记录真实首轮可用率、身份通过率和衣装通过率，再根据项目基准确定阈值，不提前写入未经校准的通用百分比。

## 十三、从现有视觉原型吸收什么

保留：

- `source_truth`；
- `required_anchors`；
- `forbidden_drifts`；
- 多候选与 dry-run；
- 跨角色防撞；
- face drift、outfit mismatch 等失败分类；
- 不把生成结果反写人物正典的边界。

重新实现或删除：

- 固定八态和仙古／凡尘枚举；
- 公共层固定仙侠画风；
- 每角色多份 runtime Markdown 镜像；
- 九宫格作为唯一身份输入；
- 长篇 production prompt 作为主要资产；
- 自然语言“权重 1000”等伪模型控制；
- 只检查文本关键词的 linter 充当图片验收；
- 单张 identity image 的整图 edit；
- 文件保存成功即视为生成成功；
- provider、endpoint 和路径硬编码；
- 普通 Git 直接保存全部大图。

## 十五、测试计划

### 15.1 CharacterTruthResolver 单元测试

## 十六、分阶段实施

### 阶段一：真源解析

- 抽取 `CharacterTruthResolver`；
- 收敛 characters root/card 配置；
- 改造 characters RAG 复用 resolver；
- 完成歧义、缺卡、路径和 stale 测试；
- 实现 `sw visual inspect`。

完成判据：任何角色在调用 provider 前都能得到唯一、可追溯、可验证的三卡结果。

### 阶段二：协议与项目模板

- 定义 identity/outfit/style pack；
- 定义 render spec 和 run manifest；
- 增加 `visuals` feature 和项目目录模板；
- 实现 `prepare`、状态机和 dry-run；
- 创建 `character-visualizer` Skill。

完成判据：不调用真实模型，也能生成完整、不可变、可验证的 job。

### 阶段三：首个 Provider 闭环

- 实现首个多参考 adapter；
- 实现 `render`；
- 保存真实请求和输出 manifest；
- 实现基础技术、身份和衣装检查；
- 实现 `approve`。

完成判据：一个三卡齐全的角色完成 identity → 三套 outfit → 每套五个不同 scene → repair → approve 全链，共形成十五张可审核场景图。

### 阶段四：稳定性提升

- 建立多角色基准集；
- 校准身份相似与跨角色间隔；
- 扩充衣装属性检查；
- 根据真实失败数据加入第二 provider 或更强控制后端；
- 增加模型升级回归测试。

完成判据：模型或 adapter 升级后，可以用同一基准集判断脸、衣装和审美是否退化。

## 十七、实施前尚需决定

以下事项不影响总体架构，但在开始对应阶段前必须确定：

1. 首个 provider 及认证配置位置；
2. 大图采用 Git LFS 还是对象存储；
3. 首个试点角色；
4. 首批三套 outfit 的项目自由命名和设计 brief；
5. 第一版是否只做人工审美批准，还是同时接入自动脸部相似度；
6. `visuals/` 是否全部版本化，或只版本化 manifest 与 approved 引用；
7. identity/outfit/style pack 的最终序列化格式采用 TOML 还是 JSON。

这些参数保持在本文，不进入 `characters/` 或公共默认值；作者确认后再进入代码实现或项目配置。

## 十八、落地路由与蓝图退出

- 公共 Skill、CLI、schema、provider adapter 与测试进入 `story-writer` 源码仓；
- 项目启用配置、批准视觉资产和项目画风进入对应写作项目；
- 人物事实修改仍只由作者明确触发后进入 `characters/`；
- 候选图、运行日志、QC 和重试记录留在 `.story-visuals/`；
- provider 拒绝、限流或内容限制只形成运行失败，不反向修改人物真源；
- 实现完成后，以 `story-writer` 源码、发布模板和项目 manifest 为实际执行真源；本文转入 `.analysis/archived/`，不继续作为第二份工具规范。

## 十九、完成定义

本能力只有同时满足以下条件才算完成：

- 公共层没有任何具体角色、服装类型或画风类型；
- 自动生成前强制验证主卡、形象、衣装三卡齐全；
- 角色解析不会模糊选人，也不会取任意 Markdown；
- 人物卡仍是唯一故事人物真源；
- 每个 approved identity/outfit/style pack 都能追溯正式来源和 hash；
- 每张 accepted 图片都能追溯输入参考、模型、参数、父图和审核结果；
- 同一角色能够稳定使用同一张脸生成至少三套服装；
- 每套批准服装能够跨至少五个不同场景保持结构和识别点；
- 首轮试点十五张批准场景图都能被作者识别为同一角色，且不会串用其它 outfit；
- 局部错误可以局部修复，不必整张重抽；
- 作者可以直接选出愿意保留使用的漂亮图片；
- 整条链不自动修改 `characters/`。

最终工作链固定为：

```text
人物三卡真源
→ 严格资格门禁
→ identity pack
→ outfit packs
→ style pack
→ 场景生成
→ QC
→ 作者批准
→ 可追溯的视觉生产资产
```
