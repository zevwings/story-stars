# 衣装 Catalog 渐进拆分与收录计划

> 状态：分析蓝图，非故事真源，非 Catalog 收录结果。
>
> 本文只规定后续如何分析、拆分和收录，不直接建立任何 `CLO-*`。人物衣装、施工事实和 Catalog 记录仍分别以各自正式文件为准，正式文件不得反向依赖本文。

## 一、目的

将言溪、秦瑶、俞予安、王诗悦、何雯娜、童颜现有衣装资料逐步整理为可复用、可查重、可转写的 Clothes Catalog，同时避免以下问题：

- 把一整套具有固定视觉身份的造型机械拆成零件；
- 把鱼骨、抽褶、系带等设计语言误建成 `piece`；
- 因角色不同或颜色不同而重复建立同一件衣装；
- 用旧分析文档覆盖当前人物衣装和当前施工事实；
- 在 ID 协议尚未升级时写入不符合最终编号格式的记录；
- 为追求一次性完成而把衣装压缩成一句话或几个标签。

本计划采用“每次处理一套或一个自然批次”的方式：先还原完整衣装，再判断是否需要拆分，作者确认后才进入正式 Catalog。

## 二、范围与非目标

### 本轮范围

- 盘点六名角色的现有正式衣装与相关施工证据；
- 确定 Catalog 的五位 ID 契约；
- 规定 `look`、`piece`、颜色款和双人套装的拆分边界；
- 安排后续逐批分析顺序；
- 固化第一批言溪衣装的候选结论。

### 本轮不做

- 不创建、预约或占用任何 `CLO-*`；
- 不修改人物 `衣装/`、当前 `story/construction/` 或正文；
- 不把旧分支施工直接迁入当前正式层；
- 不预先宣称最终会产生多少个 `look` 或 `piece`；
- 不把 Catalog 候选当成人物已经采用的衣装；
- 不修改 Clothes Specialty 协议、Skill、validator 或版本号。

## 四、Catalog ID 契约

### 4.1 新编号空间

- Catalog 当前只有目录索引骨架，没有任何正式 `CLO-*` 衣装实体，因此从 `CLO-00001` 开始；
- ID 固定为五位数字：`CLO-00001`、`CLO-00002`……；
- 旧四位原型、旧 reservation 和旧分析编号不占用新 Catalog ID；
- ID 一经正式分配不得复用，删除或迁出记录也不得回收；
- 编号只能单调递增，允许因取消或失败留下空缺；
- 颜色、角色、类型和目录不编码进 ID。

这项决定取代此前关于 `CLO-0230` 或四位 `CLO-0001` 起步的分析结论。旧编号属于旧原型体系，不应污染当前空 Catalog 的新编号空间。

### 4.2 写入前置门禁

当前 Clothes Specialty 的协议、Skill、validator 和测试仍需统一支持五位 ID。正式写入第一条 Catalog 记录前，必须先完成：

1. 在 story-writer 的下一 Clothes Specialty 版本（预计 `0.0.7`）中把 ID 格式改为 `CLO-\d{5}`；
2. 同步修改协议、模板、validator、fixture 和相关测试；
3. 明确空 Catalog 的起始序号与永久 high-water mark 行为；
4. 发布并安全升级 story-stars 的 Clothes Specialty；
5. 验证 `resolve ready=true`，并验证首个可分配 ID 为 `CLO-00001`。

在以上门禁完成前，本文只能记录候选名称和预期路径，不能实际预约或写入 ID。

## 五、实体拆分规则

### 5.1 先判断完整造型是否有独立身份

满足以下任一条件时，优先作为 `look` 保留完整性：

- 明确的 COS、制服、礼服、舞台服或主题套装；
- 上下装、配饰、鞋袜共同构成不可替换的固定视觉身份；
- 拆开后会丢失角色扮演、场景功能或叙事辨识度；
- 实际使用时以“一整套”被选择、穿着和识别。

`look` 可以是 `single-piece`，也可以是 `multi-piece`。`multi-piece` 不等于必须继续拆成多个 Catalog `piece`。

### 5.2 只有独立复用的实物才建立 piece

候选必须同时满足以下条件，才适合建立 `piece`：

- 是可以单独穿着、替换、借用或重复搭配的实际衣物或配件；
- 离开原套装后仍有稳定名称、结构和使用边界；
- 后续查重、搭配或转写确实会以它为独立单位；
- 建立独立记录不会造成信息比原完整造型更碎、更难用。

以下内容不能单独建立为 `piece`：

- 鱼骨、抽褶、开衩、交叉带、包边等结构或工艺；
- “甜辣”“轻熟”“纯欲”等风格词；
- 单纯的露肤区域、轮廓效果或镜头效果；
- 只服务于某套固定造型、离开后没有独立身份的装饰零件。

每批允许得出“一个 `look`、零个 `piece`”的结论，不为凑数量强拆。

### 5.3 一套衣装的分析深度

每个候选至少应说明：

- 整体身份与主要用途；
- 主色、辅色、金属色和色彩分区；
- 上身、下身、鞋袜、配饰及相互连接关系；
- 版型、材质、纹样、边缘与关键工艺；
- 前后左右的视觉重点；
- 穿脱顺序、固定方式和可替换部分；
- 站立、坐姿、行走、舞动等动作限制；
- 适用场景、镜头功能和不适用边界；
- 与现有 Catalog 候选的重复或近似关系；
- 最终为何保留为 `look`，或为何拆出某个 `piece`。

不得以“一条黑裙”“红黑 COS”这类一句话概括代替完整记录。

## 六、颜色规则

- ID 永远不带颜色；
- 每条记录正文必须写清准确色系、色彩位置、材质造成的明暗差异；
- 当颜色是造型身份的一部分时，名称应保留颜色，例如固定的“红黑暗金战袍”；
- 同一结构仅有普通换色时，原则上保留为一条 `piece`，在正文登记颜色款信息，不为每个颜色重复建 ID；
- 换色同时改变材质、结构、用途或叙事身份时，再判断是否已经是不同实体；
- 判断依据是“是否仍是同一件可替换颜色款”，而不是名称中是否出现颜色词。

## 七、双人组与共享衣装规则

俞予安、王诗悦存在多套黑白镜像或双人组合。此类衣装必须作为一个自然批次共同分析，不能按角色各建一份重复 Catalog。

判断顺序如下：

1. 先确认双人组合本身是否具有不可拆的主题身份；
2. 再确认黑、白两套是否只是同一双人 `look` 的两个角色位；
3. 如果单侧离开组合后仍可独立复用，再评估是否需要子 `piece` 或独立 `look`；
4. 两名角色的正式衣装 owner 可以各自自足，但 Catalog 只保留一个共享参考实体；
5. 只有结构、材质或用途确实不同，才允许建立不同 CLO，不因 owner 不同而复制。

Catalog 用于提供参考身份和查重，不替代两名角色各自的正式衣装文件。

## 十、单批工作流程

每一批严格按以下顺序推进：

1. **读取正式 owner**：读取人物衣装、当前施工和必要的正文闭包；
2. **读取旧证据**：只提取不冲突的详细结构、材质、颜色、穿脱和动作信息；
3. **重建完整造型**：先写出足够详细的一整套衣装，不先拆零件；
4. **判断实体边界**：决定 `look`、`piece`、共享双人实体及颜色款关系；
5. **执行撞型检查**：与已确认候选和正式 Catalog 对比结构、用途、颜色款和 owner；
6. **输出分析结论**：列出保留项、拆分项、不拆理由、冲突裁决和待确认问题；
7. **作者确认**：作者明确认可名称、边界、用途和拆分结果；
8. **预约并写入**：只有五位 ID 门禁已通过，才分配下一个 ID 并建立正式记录；
9. **验证**：检查 ID、路径、H1、frontmatter、索引、引用和 high-water mark；
10. **进入下一批**：上一批验收后再开始，不预先锁死后续编号。
